# Implementation plan for the next overhaul

Status: **implementation in progress**. The [progress ledger](PROGRESS.md) records the Foundry runtime and courtyard delivery, partial packages, and remaining work. This plan follows the [game design](DESIGN.md) and the user's reference-based [art standard](ART_STANDARD.md). The main campaign remains the v2 prototype at baseline `2259a28`.

The next milestone is a polished three-encounter slice that demonstrates the new foundations. The full campaign comes after that milestone. There is no reliable completion date until the asset sourcing/creation pass establishes how many usable models and animations already exist.

## Delivery and ownership

Develop the preview at `/next/`, served at `/NeonKnights/next/` by the Pages repository base path. Add it as a Vite multi-page entry with its own new-runtime dependency graph. Keep the existing root build available for comparison during development. The new entry uses one Three.js renderer; it does not boot Phaser or the old CanvasTexture renderer.

Retain useful infrastructure after checking its contracts: seeded random utilities, fixed-step simulation, explicit damage attribution, save/settings separation, focus-loss pause, remapping, reduced motion, static deployment and the original Classic archive. Existing gameplay types and balance values are not compatibility constraints for the new design.

| Existing area                        | Next implementation                                                                                                                                               |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/main.ts`, `BattleRenderer.ts`   | Keep serving v2 while the preview gets a new bootstrap, scene lifecycle, asset loader, camera and skeletal presentation layer                                     |
| `InputController.ts`                 | Reuse remapping patterns; replace sector movement and summon input with move/aim/dodge, selection, orders and touch equivalents                                   |
| `RunState.ts`, `types.ts`            | Introduce a v3 state schema for world surfaces, commander health, persistent company, inventories, structures and hazards                                         |
| `CombatSystem.ts`, `WeaponSystem.ts` | Preserve explicit attribution as a design; replace direct boss damage and generic weapon presentation with contact-based abilities and synchronized action states |
| `EnemySystem.ts`, `WaveDirector.ts`  | Replace stationary boss loops and fixed entry schedules with navigation, authored approaches, encounter budgets and per-boss state machines                       |
| `SquadSystem.ts`                     | Replace duration/cooldown summoning with roster lifecycle, persistent orders, formation slots, reservations and equipment behavior                                |
| `EconomySystem.ts`, `UI.ts`          | Replace one three-card market with Construction, Armory, Garrison and Relics; separate ownership from equipped slots                                              |
| `storage.ts`                         | New versioned save namespace and validation; preserve old saves/settings without treating temporary v2 knights as recruited characters                            |
| `tools/blender/render_atlas.py`      | Retain as historical tooling; new assets export skinned GLBs and metadata, without directional sprite rendering                                                   |
| `tools/balance.ts`                   | Retain as v2 evidence; create varied behavior policies and progression diagnostics for the new rules                                                              |

Proposed v3 modules belong under `src/next/` while both versions coexist. Split `world`, `combat`, `company`, `economy`, `presentation`, `ui` and `persistence` by responsibility. Data definitions refer to stable asset and ability IDs; UI components do not implement combat calculations.

## Ordered work packages

Each package requires its stated evidence before dependent work can be called finished. Limited graybox work is useful for proving a rule; the art review cannot accept grayboxes as the playable milestone.

### R00 — Record the prototype's failure modes

**Dependencies:** none. **Status:** diagnostic/design work completed in this package.

- Record boss movement, actual damage, interrupt behavior, natural spawn schedule and a saturated shop from the unchanged baseline.
- Preserve the player's eight observations beside the redesign and retain the old automated campaign results as reachability evidence only.

**Evidence:** [controlled baseline audit](evidence/v2-audit.json), generated by `tools/review/audit-v2.ts`. It shows zero boss movement, real but visually weak fortress-damage events when unopposed, a developed Stormbow defeating the isolated Dragon without a committed damage event, and three fortress offers for a saturated wave-11 build. The controlled loadout and test duration are recorded; this does not estimate human win rate.

### R01 — Establish the preview runtime and asset viewer

**Dependencies:** R00.

- Add the `/next/` entry, a pinned Three.js dependency and explicit asset loading/error states.
- Create scene cleanup, fixed-step update/interpolated presentation, camera controls for inspection, lighting and model selection.
- Load one real skinned test asset, give two instances independent animation state and expose a clip/speed/weapon-socket viewer in development.
- Keep frame-capture and model metrics available in development; do not expose state mutation helpers in the production preview.

**Evidence:** browser playback of exported skeletal animation, smooth arbitrary orientation, independent actors, clean reload/dispose, correct Pages base paths and a measured initial render. A rotating unanimated model does not pass.

### R02 — Produce and accept the hero art pipeline

**Dependencies:** R01. **First quality gate.**

- Inventory suitable authored/source assets against the reference. Select a coherent source set or build missing art in Blender; record the actual gaps, source terms and animation cleanup needed.
- Complete the commander, Stormbow, Sunlance and the shared humanoid movement set. Build a real deformation rig, painted materials, weapon sockets and baked export clips.
- Implement the export manifest and validation described in the art standard. Keep source and exported runtime versions traceable.
- Review neutral turntables, locomotion, hands/string/release, weapon swaps, slow time and battle-camera readability.

**Evidence:** the commander looks at least as finished as the user's reference in the browser; both weapons are correctly held and animated. If the quality is insufficient, continue art work before multiplying the character roster. A procedural blockout does not close this package.

### R03 — Build navigable terrain and direct commander combat

**Dependencies:** R01; visual acceptance depends on R02.

- Author the inner loop, two outer approaches, gate, ramp and one breachable wall section.
- Add surfaces, height sampling, ramp links, collision, traversal reachability and camera occlusion fading.
- Implement independent movement/aim, two recoverable dodges, health/downed/rescue and weapon switching.
- Prevent stuck input when order mode, pause or focus changes. Add equivalent touch actions with selection that does not accidentally fire.

**Evidence:** a player can circle the courtyard, reach the battlement, retreat through the gate, fight on the ramp and cross a breach without teleporting, falling through geometry or aiming through an invalid height. Movement meaningfully avoids a real attack.

### R04 — Implement shared ability and hazard rules

**Dependencies:** R03.

- Define approach, telegraph, commit, active hazard, recovery, interruption and resolve states.
- Add projectiles, swept cones/arcs, circles, lingering ground effects and explicit target masks/height rules.
- Derive danger meshes and collision from the same shape data. Link animation timing and sockets to simulation-owned release/contact moments.
- Support wall/building/knight/commander damage and attribution, line of sight, destruction and clean expiry.
- Specify hit deduplication and periodic-damage cadence so a frame-rate change cannot multiply damage.

**Evidence:** focused simulation tests for crossing a hazard between steps, one contact versus sustained damage, target masks, committed-attack behavior and slow-time consistency. Browser footage shows the same shapes with debug geometry on and off.

### R05 — Add ordinary enemy roles and encounter staging

**Dependencies:** R02–R04.

- Produce accepted Raider, Bulwark and Hexcaster assets and action clips.
- Implement reachable attack positions, enemy avoidance, shield facing and break rules, physical melee and projectile attacks.
- Build visible staging and approach paths, then a director that schedules role combinations and overlapping jobs under a threat budget.
- Add a supply objective and a gate/breach change that alter route decisions.

**Evidence:** all three roles threaten the appropriate target, have distinguishable silhouettes and preparation, and can attack without clipping or merely queueing on one point. At least one encounter requires repositioning or an order change to protect two objectives.

### R06 — Replace summons with a persistent company

**Dependencies:** R03–R05.

- Create named roster records, active/reserve slots, roles, health, service experience, traits and equipment ownership.
- Add move/hold/focus/protect/retreat orders, stable formation slots, path-following, avoidance, attack-position reservations and a pursuit leash.
- Implement Warden brace/block and Marksman firing distance. Orders persist while the commander fights elsewhere.
- Add downed rescue, wounded recovery, reserve substitution and bounded treatment. Knights and equipment persist through encounter transitions.
- Use accepted role models, locomotion, attacks and visible equipment swaps from the art pipeline.

**Evidence:** three knights defend for longer than 12 seconds without expiring, hold distinct positions, navigate a narrow gate, retreat out of a Dragon-sized danger area, survive a planning transition and retain reassigned equipment. One additional recruit can enter reserve and replace an injured active member.

### R07 — Make construction a modeled, inspectable choice

**Dependencies:** R03–R05 and accepted building assets.

- Add the Construction catalogue, placement ghost, suitable sockets, capacity accounting, orientation, coverage preview and tier comparison.
- Produce Ballista and Aegis at all three tiers, with their working mechanisms and branch fittings.
- Implement physical bolts/recoil and directional shield contact, plus damaged and destroyed states.
- Add planning relocation, explicit salvage, repair and known-price upgrades. A failed purchase cannot charge gold or leave a half-created structure.

**Evidence:** the player can choose either family, inspect every tier, orient it, observe its effect in combat and move or salvage it. Tier silhouettes pass the neutral-light review. Shield coverage and firing arcs agree with the preview.

### R08 — Build separate progression and equipment screens

**Dependencies:** R06–R07.

- Create Construction, Armory, Garrison and Relics navigation with a persistent resource summary and clear planning/combat availability.
- Separate owned inventory, equipped weapons, per-weapon sockets and company equipment.
- Keep purchased weapon ranks, enable two-weapon loadouts and free planning-time rune removal/reassignment.
- Add six stable market offers, explicit section rerolls, compatible-gear previews and purchasable known improvements independent of random stock.
- Bound fortress maximum-health progression. Repair only restores missing health.

**Evidence:** purchase multiple offers without losing the remaining stock; store and equip a different rune with full sockets; swap Stormbow/Sunlance without losing investment; reassign a knight's item; verify transaction atomicity, save/load and no reroll/sale duplication exploit.

### R09 — Produce the Dragon and its actual fight

**Dependencies:** R04–R07; dedicated Dragon art production can begin once R02 establishes the pipeline.

- Complete its skeleton, materials, flight/ground transitions, four attack patterns and damage/death states.
- Add visible entrance staging, valid landing/reposition choices, sweeping breath/scorch, talon impact, tail sweep and wall rake.
- Implement discrete weak-point openings, finite stagger, post-interrupt resolve and committed attacks that survive ordinary incoming damage.
- Make a wing break change both the model and the subsequent flight behavior. Ensure no eligible attack location can deadlock the fight.

**Evidence:** a diagnostic scene and a normal encounter each show movement, every resolved ability, damage to the correct target, a successful dodge, a successful interrupt, an attack committing after resolve, a rescued knight and a physical death. Boss text can be hidden without making the fight incomprehensible.

### R10 — Deliver legendary rules and crafted plates

**Dependencies:** R07–R09.

- Implement Worldpiercer, Oath of the Storm King and The Black Standard with explicit trigger/target/limit rules and their physical conversion, gear or banner.
- Create their modeled/rendered item artwork, authored material palettes and restrained foil/chroma plates.
- Show resolved effects, compatibility, costs, tradeoffs and a before/after preview; support reduced motion and keyboard/touch inspection.
- Award a three-choice relic cache after the first boss. Allow stored rewards and a viable path to the compatible building or equipment so a late discovery can support a pivot.

**Evidence:** each legendary creates its described behavior in combat, respects its limit and changes the model/effect. The plate explains that behavior accurately without requiring the player to infer it from a name or rarity color.

### R11 — Assemble the first playable siege

**Dependencies:** R02–R10. **Second quality gate.**

Use three encounters, with a target of 5–8 minutes of combat plus readable planning breaks:

1. **Hold the gate:** introduce direct combat, one Warden/Marksman order and the construction choice. A supply threat creates a reason to leave the starting position.
2. **Dragon assault:** staged arrival and a moving boss with real hazards; the company needs orders and at least one recovery decision. Earn the relic cache.
3. **Counter-siege:** a compact combined threat tests the chosen legendary, a building upgrade and a possible equipment pivot. The reward is used before the slice ends.

Initial roster: two Wardens and one Marksman, with one recruitable reserve. Equipment: Stormbow plus an obtainable Sunlance, a small but complete rune set, visible knight-item swaps, two buildings at three tiers, and three legendary alternatives.

Costs and initial resources must let the short slice demonstrate high tiers without pretending they are the campaign's final progression curve. Label preview balancing clearly. Do not allow developer currency or invulnerability to leak into normal playtest footage.

**Evidence:** an ordinary playthrough shows the new art, combat, construction, company and legendary interaction together. Capture desktop and touch layouts, check audio/VFX clarity, and publish the actual build at `/next/` for feedback before adding the rest of the campaign.

### R12 — Extend content using the accepted pipeline

**Dependencies:** R11 and resolution of major playtest findings.

- Complete Lancer and Chanter, the remaining three commander weapons and their true action sets.
- Build Chapel, Ossuary and Barracks/workshop through three tiers; add further families only with the same modeled and animated quality.
- Add the walking, destructible-limb Golem and moving banner/decree King with unique rigs/patterns where needed.
- Expand battlefield approaches and authored encounter combinations. Reuse systems and finished materials, while retaining distinct roles and silhouettes.

**Evidence:** every newly added asset passes the same inspection and runtime checklist; every boss ability is demonstrated as both a threat and a counterable action. No temporary creature drawings return to fill the roster.

### R13 — Tune a campaign with choices after wave 11

**Dependencies:** R12.

- Define act budgets for income, construction capacity, weapon ranks/sockets, recruit slots, equipment, promotions and legendary rewards.
- Add meaningful late specializations and build pivots; reserve progression beyond the opening act instead of exhausting all systems by wave 11.
- Test weak/ordinary/strong builds with varied spending and input policies, plus human runs with incomplete mechanical knowledge.
- Instrument danger response, company participation, damage sources, idle gaps, remaining affordable decisions and compatibility of offers.
- Revise enemy composition/tempo and opportunity cost before using large HP increases to manufacture difficulty.

**Evidence:** passive play fails meaningful encounters; ordinary active play remains learnable; strong play is rewarded; no tested legal developed build is trapped in a fortress-only shop. Wave-11 planning still presents at least three relevant opportunities across systems. Perfect bot victories are recorded separately from difficulty judgments.

### R14 — Persistence, performance and release hardening

**Dependencies:** complete candidate content; begin profiling during R01/R02.

- Use a separate `neon-knights:v3` save family with versioned planning checkpoints. Import compatible preferences explicitly; preserve v2 checkpoint/profile data rather than guessing a conversion for incompatible gameplay.
- Validate inventories, equipment ownership, unique IDs, roster assignments, buildings, resources and unlocked milestones when loading. Recover cleanly from invalid saves.
- Profile representative fights on named hardware and browsers. Verify loading/error/retry, context loss, resize, focus changes, touch, remapping, reduced motion and audio controls.
- Run focused simulation/economy tests, production build and browser flows; check real exported animation and combat captures as separate evidence.
- Check GLB/texture delivery, caching, licensing records for the actual assets, and total Pages artifact size. Keep editable source art outside the public artifact.

**Evidence:** a recorded candidate checklist with commit, asset versions, test results, device/frame-time data and open issues. Compare the candidate to the user reference and the eight feedback points, not just to the previous build.

### R15 — Publish and promote the verified build

**Dependencies:** R14; the early preview publication is part of R11.

- Push the candidate through the existing Actions-based Pages workflow and verify its run, deployed URLs and loaded asset revision.
- Open the deployed preview, finish representative combat and planning actions, reload its checkpoint and check the browser console/network.
- Promote the new runtime to the main game entry only when the complete candidate passes its checks and the preview's critical playtest issues have been resolved.
- Retain an explicit rollback route/commit and keep the Classic archive intact.

**Evidence:** a working public link, successful deployment and a concise release note distinguishing completed work from remaining content or performance limits. Do not call a design document, mocked UI, source render or untested artifact a shipped overhaul.

## Test and review priorities

Automate rules that can regress: navigation/height boundaries, hazard contact, animation timing metadata, interrupt/resolve transitions, roster/equipment ownership, economy transactions, persistence and progression availability. Use small seeded scenarios with explicit expected outcomes.

Review visually what automated tests cannot judge: reference-level craft, hand/weapon contact, foot sliding, attack weight, tier desirability, card readability, crowd spacing and boss danger. Record normal play as well as isolated diagnostics. The previous version's passing tests did not establish those qualities.

The first release milestone closes only when a player can say: **the commander and enemies look finished; their attacks physically happen; the fortress grows visibly; and the knights are worth keeping alive.**
